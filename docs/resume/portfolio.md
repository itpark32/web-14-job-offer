# Портфолио Frontend-разработчика

**Два сильных проекта лучше десяти незаконченных.** Выберите работы, которые показывают нужные для вакансии сценарии и отличаются задачей: например, качественная адаптивная верстка и приложение с API и состоянием.

Отдельный сайт-портфолио необязателен. Достаточно понятного GitHub, карточек проектов и доступных demo. Не тратьте неделю на оболочку, пока главный проект не открывается.

## Как выбрать 1–2 работы

| Вопрос | Признак готовности |
|---|---|
| Какую задачу решает приложение? | Можно показать полезный сценарий за минуту |
| Что сделал лично? | Есть конкретные файлы, решения и проверка |
| Соответствует ли роли? | Подтверждает ключевые задачи целевой вакансии |
| Можно ли проверить? | Repo, README, screenshot и demo доступны |
| Можно ли обсуждать? | Объясняете альтернативу, ошибку и ограничение |

Не добавляйте Redux, routing или тестовую библиотеку только ради списка. У каждого инструмента должна быть задача. Улучшения выбирайте по [проектам курса](project-to-portfolio.md).

## Минимальная карточка

```text
Название / учебный, личный или командный:
Пользователь и проблема:
Repo / Demo / Screenshot:
Реальный стек:
Что сделал лично:
Основной сценарий:
Архитектурное решение и альтернатива:
Сложность / ошибка / способ проверки:
Что улучшил бы:
```

## Порог готовности к откликам

Не превращайте этот список в условие «сначала сделать идеальный проект, потом искать работу». Для первых откликов достаточно рабочего и объяснимого результата. Остальное улучшайте параллельно с поиском.

### Обязательно перед первыми откликами

- [ ] Репозиторий открывается и содержит актуальный код.
- [ ] Основной пользовательский сценарий работает.
- [ ] Есть понятный README с назначением и запуском.
- [ ] Есть screenshot или другое быстрое представление результата.
- [ ] Demo открывается, если проект можно разумно опубликовать.
- [ ] В репозитории нет секретов, токенов и закрытых данных.
- [ ] Вы можете объяснить свой личный вклад и основные решения.
- [ ] Вы можете самостоятельно внести небольшое изменение в проект.

Если публичное demo объективно не нужно или невозможно, честно объясните причину и предложите доступный способ показать результат. Инструкцию запуска дополните `.env.example`, если нужны переменные окружения.

### Желательно

- [ ] Интерфейс проверен на desktop и mobile.
- [ ] Формы и основные элементы можно использовать с клавиатуры.
- [ ] Loading, error и empty states обработаны там, где они применимы.
- [ ] Browser console не содержит необъяснённых ошибок.
- [ ] История Git содержит понятные изменения, а не только один финальный commit.
- [ ] README содержит ограничения проекта и дальнейшие улучшения.

### Усиление проекта

- [ ] Есть тесты важных пользовательских сценариев.
- [ ] Проведена базовая проверка accessibility.
- [ ] Проверена производительность и устранена хотя бы одна измеренная проблема, если она есть.
- [ ] Есть осмысленное архитектурное улучшение.
- [ ] Есть более сложный сценарий работы с API или состоянием.
- [ ] Подготовлено объяснение альтернативного технического решения.

Эти пункты не являются условием начала поиска. Добавляйте их по требованиям вакансий и по обратной связи с реальных интервью.

Для статической верстки сетевые состояния могут быть неприменимы — отметьте это, не имитируйте их ради чек-листа. Готовый [portfolio checklist](../templates/index.md#portfolio-checklist) можно скопировать.

Если не хватает понимания компонента, состояния или качества, используйте [карту технической подготовки](../technical/developer.md). Здесь задача — сделать доказательство навыка доступным работодателю.

## Что сделать прямо сейчас

1. Сравните имеющиеся проекты с тремя задачами вакансии.
2. Оставьте одну основную и одну дополнительную работу.
3. Заполните карточку и устраните блокеры просмотра.
4. Запишите рассказ о проекте на две минуты.
