# Frontend code review на интервью

Начните с цели изменения и пользовательского сценария. Review проверяет, умеете ли вы найти существенный риск и предложить понятное исправление.

## Порядок просмотра

| Приоритет | Что спросить |
|---|---|
| Корректность и пользователь | Решена ли задача, работает ли основной сценарий? |
| Ошибки и данные | Что случится при сбое API, пустом ответе, быстрых действиях? |
| Поток данных и состояние | Есть ли противоречивые данные и понятен ли их владелец? |
| Доступность | Можно ли выполнить действие клавиатурой, понятны ли подписи? |
| Тесты | Проверяется ли риск и наблюдаемое поведение? |
| Читаемость | Понятны ли границы, имена, причины решений? |
| Производительность | Есть ли подтверждённая проблема, которую нужно измерить? |
| Стиль | Соответствует ли код договорённостям команды? |

Не начинайте с кавычек, если приложение показывает неверную сумму. Порядок помогает расставлять акценты; конкретная критичная проблема важнее формального списка.

## Небольшой учебный пример

Изменение добавляет кнопку «Повторить поиск». У неё нет доступного имени, а при втором запросе на экране остаётся прежняя ошибка.

**Слабый комментарий:** «Плохой компонент, надо переписать».

**Полезный комментарий:** «После ошибки нажимаю повтор; успешные данные появляются вместе со старым сообщением. Пользователь не понимает, завершился ли запрос. Предлагаю согласовать переход состояния при повторе и проверить последовательность error → retry → success».

Отдельно: «У кнопки с одной иконкой нет понятного имени; проверьте её в дереве доступности и с клавиатурой». Сначала опишите риск, затем предложите направление исправления и сценарий проверки. Не превращайте пример в лекцию о React.

## Как говорить на секции

Разделяйте блокер, вопрос и предпочтение. При недостатке контекста спросите об API-контракте и требованиях. Не заявляйте о медленном рендере без измерения. В конце назовите 2–3 главных риска и порядок исправления.

Технические критерии повторите в [качестве и архитектуре](https://itpark32.github.io/web-14-metodichka/interview/quality/), работе с состоянием — в [React](https://itpark32.github.io/web-14-metodichka/interview/react/).

## Что сделать прямо сейчас

1. Возьмите небольшой учебный diff.
2. Пройдите основной и ошибочный сценарии.
3. Напишите три замечания: риск, исправление, проверка.
4. Отделите блокеры от вопросов и стиля.
