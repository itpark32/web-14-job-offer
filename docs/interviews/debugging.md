# Debugging: показать ход диагностики

На секции важно связать наблюдение, гипотезу и проверку. Не перечисляйте DevTools-вкладки без цели и не меняйте несколько вещей наугад.

## Последовательность

**Симптом → воспроизведение → Console / Network / DOM / state → гипотеза → проверка → исправление → повторная проверка.**

| Шаг | Что произнести или сохранить |
|---|---|
| Симптом | Ожидаемый и фактический результат, экран, момент появления |
| Воспроизведение | Минимальные шаги, данные, браузер и ширина экрана |
| Наблюдение | Первая полезная ошибка, статус/ответ запроса, DOM или состояние |
| Гипотеза | Одна предполагаемая причина и способ её опровергнуть |
| Проверка | Breakpoint, изменение условий или минимальный пример |
| Исправление | Изменение подтверждённой причины |
| Повтор | Тот же сценарий и соседний случай; regression-тест при необходимости |

## Учебный кейс: пустой экран после поиска

1. Уточните: проблема для любого имени или только неизвестного пользователя?
2. Повторите на обычном и отсутствующем имени.
3. Посмотрите Console и ответ в Network. Не называйте причину до наблюдения.
4. Если ответ об ошибке обрабатывается как данные профиля, сформулируйте эту гипотезу и покажите место перехода в UI.
5. Исправьте обработку, проверьте ошибку, повторный успешный поиск и состояние загрузки.

Это сценарий диагностики, а не утверждение о любом проекте Finder. На интервью фактическая причина может быть другой.

## Если не удалось найти причину

Подведите промежуточный итог: что воспроизводится, что исключили, какое наблюдение осталось и какой следующий эксперимент. Спросите о доступных данных. Не выдавайте предположение за доказанный баг.

Для практики инструментов используйте [Browser tools](https://itpark32.github.io/web-14-metodichka/interview/browser-tools/), ошибок языка — [JavaScript](https://itpark32.github.io/web-14-metodichka/interview/javascript/), поведения компонентов — [React](https://itpark32.github.io/web-14-metodichka/interview/react/).

## Что сделать прямо сейчас

1. Возьмите один воспроизводимый баг проекта.
2. Запишите ожидаемое и фактическое поведение.
3. Проверьте одну гипотезу с объяснением вслух.
4. Сохраните исправление и шаги повторной проверки.
